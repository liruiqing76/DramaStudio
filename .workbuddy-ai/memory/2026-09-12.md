### 审计发现（全部基于 DB 实证 + 官方文档 + 真实 API 实测）

**发现的真实缺陷 3 项：**

1. **【严重】`reference` 模式与首尾帧互斥，原实现同时发送 → 成批 400**
   - 官方硬约束：`reference` 禁 `first_frame/last_frame/videos`；`keyframe` 禁 `images/audios/videos`。
   - 实测报错原文：`首尾帧素材与参考素材不能同时使用`（param: mode）。
   - 修复：`videoClient.js` 重写模式判定 —— 有参考图 → `reference` 并**丢弃首尾帧**（记日志）；否则有首尾帧 → `keyframe`。

2. **【重要】reference 素材没有语义说明 → 模型分不清哪张是角色、哪张是场景**
   - 官方（agnes-video-25「提示词建议」）：reference 模式**应**在 prompt 里写出 `<Picture N>` 及其用途，
     "比只上传素材但不解释用途更容易获得可控结果"；「编号规则」= images 数组从 1 开始编号。
   - 原实现只丢 `images` 数组，prompt 从不提占位符。实测：不写也能 200，但可控性无保障。
   - 修复：
     - `videoService.resolveStoryboardVideoReferences()` 改为返回**带标签**的 `[{ref, kind:'character'|'scene', name}]`，
       并调整顺序为**角色定妆图在前、场景图在后**（便于 `<Picture 1..k>` 指代角色）。
     - `videoClient.js` 新增 `buildAgnesPictureReferencePrefix()`，在清洗后的 prompt 前拼接
       `以 <Picture 1> 中的角色「林风」外貌、发型与服装为参考，保持角色一致性；以 <Picture 2> 的场景环境…为背景。`
     - 顺序关键：先 `adaptPromptForAgnes` 清洗，**再**加前缀（否则标签规则会误伤前缀）。
   - 实测：修复后 E2E 提交 HTTP 200，mode=reference，prompt 含 `<Picture 1/2>`。

3. **【重要】`configs/config.yaml` 的 `image_proxy.use_for_video: true` 主动把本地图送第三方图床**
   - 这是 34 次失败的真正开关：`port 5679 is not allowed` ×23、`download input image failed: HTTP 404` ×11。
   - 修复：改为 `false`（默认走 Data URI Base64 直传，官方明确支持），并补注释说明。
   - 实测：base64 双图合计 3.82MB → HTTP 200，第三方图床已完全移出链路。
   - 另把 `toPublicMedia` 里吞异常的 `catch (_) {}` 改为记 `log.warn`，并在"优先 base64 但拿不到本地图"时显式告警，
     避免静默回退图床。

## 修复 Git 凭据助手反复弹窗（CredentialHelperSelector）

**症状**：每次 `git push` 都弹出 "Select a credential helper" 对话框
（选项 `<no helper>` / `manager` / `wincred` / `manager`）。

**根因（`git config --list --show-origin` 定位）**：`credential.helper` 出现**两次叠加**——
1. PortableGit 自带的系统级配置 `PortableGit/versions/1.2.0/etc/gitconfig` 里写了
   `credential.helper=helper-selector`
2. 用户级 `~/.gitconfig` 里又写了真正的
   `credential.helper=!".../git-credential-manager.exe"`
Git 的 helper 是**叠加**语义（多个依次调用），helper-selector 先触发 → 每次都弹窗。

**修复（用户级）**：
```bash
git config --global credential.helper ""          # 空值 = 清空此前累积的 helper 列表
git config --global --add credential.helper '!".../git-credential-manager.exe"'
```
关键点：**空字符串 helper 会重置整个 helper 链**，这一步才能把系统级的 helper-selector 抵消掉。
改完 `git config --get-all credential.helper` 应只剩 manager 一项。

**验证**：
- `printf 'protocol=https\nhost=gitee.com\n\n' | git credential fill` → 直接返回已缓存凭据，无弹窗
- 真实 push → 顺畅成功（`71b3a7e..e882684`）
- 注意：凭据库中存的是 Gitee **明文密码**，长期建议换成 Access Token

**相关**：`~/.gitconfig` 另有 `credential.https://ghfast.top.provider=generic`（GitHub 加速代理），
说明用户网络访问 GitHub 需代理。

## GitHub vs Gitee 讨论

用户问是否该改用 GitHub，理由是"Gitee 这个地方没法创建（仓库）"。**结论建议继续用 Gitee**：
- Gitee 仓库 `liruiqing76/MiniDrama` 实际工作完全正常（`git ls-remote` 正常返回）
- "没法创建"最可能是 **Gitee 要求实名认证才能建公开仓库**（未实名时点新建会引导认证/或只能建私有）
- 本项目有两个大文件（`ffmpeg.exe` 99MB、`example_drama/衣服设计天才302.zip` 82MB），
  **GitHub 单文件硬限 100MB**，99MB 那个已贴边，迁过去后续增长会直接爆仓库
- Gitee 国内直连快；用户在 `.gitconfig` 里配了 `ghfast.top` 代理，说明 GitHub 访问有网络痛点
- 若坚持迁 GitHub，需先处理大文件（Git LFS）
